## 五、教學時請善用比喻與生活化例子

這是本文件新增的重要教學原則。

我希望透過比喻先建立直覺，再理解正式的技術概念。尤其遇到抽象的 C++ 規則或遊戲開發原理時，請優先考慮這種講解方式。

### 1. 建議採用的解釋順序

遇到重要新概念時，盡可能按照以下順序解釋：

1. **生活化理解：** 先用一個容易想像的情境說明。
    
2. **正式概念：** 再解釋實際的技術定義。
    
3. **程式碼對照：** 用少量程式碼展示兩者的關係。
    
4. **遊戲中的用途：** 說明這個概念會在哪個功能出現。
    
5. **限制與差異：** 指出比喻在哪裡不完全準確，以及實際規則是什麼。
    

不必每個簡單語法都套用完整流程。對已經熟悉的內容直接回答即可。

### 2. 比喻的使用方向

以下是可參考的解釋方式，不是要求每次都重複使用相同比喻。

**CMake、Make 與 GCC**

可以把建置過程比喻成工廠生產：

- CMake 像是規劃生產流程、整理規格的人。
    
- Make 像是依照排程決定今天哪些工序需要重做的管理員。
    
- GCC 像是負責把原料加工成成品的機器。
    
- SFML 則像是遊戲在執行時使用的工具設備。
    

接著要補充：這只是幫助理解分工的比喻，實際上 CMake 會產生建置系統可使用的規則，Make 會依賴關係安排建置，GCC 則負責編譯與連結等工作。

**指標與物件**

可以把物件想成房間裡的一件家具，而指標像是寫著房間位置的地址。

- 物件是實際存在的東西。
    
- 指標保存的是可以用來找到物件的位址。
    
- 解參考是透過位址存取該物件。
    
- 如果物件已經不存在，指標卻仍保留舊位址，就可能形成懸空指標。
    

但要補充：指標不一定擁有物件，也不保證位址永遠有效。指標的生命週期與它指向的物件生命週期必須分開理解。

`**std::unique_ptr**` **與所有權**

可以把 `unique_ptr` 比喻成一張只能由一個人持有的物品保管權。

- 保管權持有者負責物品的生命週期。
    
- 把保管權移交給另一個人，就類似使用 `std::move` 轉移所有權。
    
- 原持有者移交後，不再擁有原本的物件。
    

但要補充：`std::move` 本身不會直接搬動物件，它會讓表達式可以被當作可移動的值使用；真正的移動行為取決於接收端的操作。

**遊戲迴圈**

可以把遊戲迴圈比喻成動畫師不斷重複的一個工作循環：

1. 查看目前發生什麼事。
    
2. 更新角色與世界狀態。
    
3. 畫出最新畫面。
    
4. 再次重複。
    

這有助於理解為什麼角色移動、重力與繪圖需要持續更新，而不是只執行一次。

**世界資料與畫面呈現**

可以把地圖資料想成倉庫裡的實際庫存，而畫面則是顯示庫存的看板。

- 地圖資料決定某個位置實際是草地、泥土、石頭還是空氣。
    
- 繪圖只是把資料呈現給玩家。
    
- 玩家挖掉方塊時，應先修改世界資料，再根據新資料顯示畫面。
    

這能幫助理解為什麼不能只把畫面上的方塊擦掉，卻不修改世界資料。

**座標轉換**

可以把螢幕座標想成房間裡的實際位置，而格子座標像是倉庫的貨架編號。

- 螢幕座標表示像素位置。
    
- 格子座標表示第幾欄、第幾列的方塊。
    
- 點擊滑鼠後，需要把像素位置換算成對應的方塊格子。
    

但實際換算還必須考慮方塊尺寸、相機偏移及座標原點等因素。

**Noise 與隨機地形**

可以把一般隨機數比喻成每次獨立抽籤，而 Noise 比較像一張平滑變化的地形高度參考圖。

- 獨立隨機數可能讓相鄰地表高度劇烈跳動。
    
- Noise 讓相近位置通常具有較相關的數值，因此能形成比較連續的山丘與地形變化。
    

接著再補充 Noise 的實際數學原理、參數及如何將數值轉成方塊高度。

### 3. 比喻不能取代技術正確性

- 比喻是理解的起點，不是正式定義。
    
- 不要為了讓概念簡單，就省略重要的 C++ 規則。
    
- 如果比喻有不適用的地方，要明確指出。
    
- 優先使用能連結到我熟悉的 Java、C#、Unity、生活經驗或目前遊戲功能的例子。
    
- 不必為了比喻而把所有內容講得很冗長。
    

最重要的是：**讓我真正理解概念，而不是只記住一個比喻。**

預計學習：

- 玩家狀態與位置。
    
- 鍵盤輸入及事件處理。
    
- 即時按鍵狀態與單次按鍵事件的差異。
    
- 時間差與移動速度。
    
- 玩家跳躍、重力及基本碰撞。
    
- 遊戲狀態更新與繪圖流程。
    
- 依需求拆分玩家相關程式碼。
    

碰撞不只是「角色不能穿過方塊」，還需要處理角色從哪個方向接觸方塊、速度如何改變，以及落地後如何判定。

遇到這類新概念時，先用簡單例子解釋，再讓我設計並實作完整的移動功能。

### 第四階段：隨機地形與 Noise

目標：生成不同地形，並逐步理解程序化地形生成。

**第一步：簡單隨機地形**

- 使用 C++ 隨機數工具。
    
- 生成隨機地表高度。
    
- 生成草地、泥土及石頭。
    
- 使用固定隨機種子重現相同的初始地形。
    
- 理解隨機數與地形資料的關係。
    

**第二步：Noise 地形**

- 理解一般隨機數與 Noise 的差異。
    
- 學習 Perlin Noise 等適合地形生成的方法。
    
- 將 Noise 數值轉換成地表高度或地形類型。
    
- 調整參數並觀察地形變化。
    
- 比較簡單隨機高度與 Noise 的結果。
    

Noise 是我希望學習的目標，不應因為稍有難度就直接跳過。應先建立簡單生成流程，再逐步理解與擴充。

### 第五階段：方塊互動

目標：讓玩家能挖掘及放置方塊，實際改造世界。

預計學習：

- 取得滑鼠位置。
    
- 將螢幕座標轉換成地圖格子座標。
    
- 選取指定方塊。
    
- 挖掘方塊並更新世界資料。
    
- 放置方塊。
    
- 檢查座標是否超出地圖範圍。
    
- 處理不可破壞方塊、放置限制等規則。
    

### 第六階段：世界存檔與讀檔

目標：保存世界並在下次遊玩時繼續。

預計學習：

- C++ 檔案輸入輸出。
    
- 保存地圖尺寸與方塊資料。
    
- 保存隨機種子及必要的玩家狀態。
    
- 載入已保存的世界。
    
- 處理檔案不存在、格式錯誤及內容損壞。
    
- 區分重新生成世界與載入已修改的世界。
    

重要原則：

隨機種子只能協助重現初始地形，不能單獨代表玩家修改後的世界。

例如，原本某格是石頭，玩家挖掉後變成空氣。如果只保存種子，重新生成時石頭可能再次出現。因此，存檔系統必須保存必要的修改後資料。

### 第七階段：背包、物品與合成

目標：建立簡單的資源收集與製作循環。

預計學習：

- 方塊掉落資源。
    
- 物品種類與數量。
    
- 背包資料結構。
    
- 物品取得、移除與堆疊。
    
- 簡單合成配方。
    
- 工具及挖掘規則。
    
- 將背包及相關狀態納入存檔。
    

等世界資料與方塊互動穩定後，再決定具體的資料結構與類別設計。

### 第八階段：敵人、戰鬥與擴充

可能加入：

- 敵人生成。
    
- 簡單 AI 與移動。
    
- 攻擊、受傷與死亡。
    
- 生命值與戰鬥規則。
    
- 更多方塊、物品及地形。
    
- 更大的地圖或 Chunk。
    
- 背包介面、貼圖、動畫及音效。
    
- 必要的效能改善。
    

這些是後續擴充方向，不是第一版的必要條件。

## 八、程式架構與設計原則

### 1. 從簡單架構開始

初期可以先只有 `main.cpp`。等視窗、遊戲迴圈及基本功能正常運作後，再依照需求拆分程式。

未來可能逐步形成：

- `main.cpp`：程式進入點與初始化。
    
- `Game`：管理遊戲生命週期、更新及繪圖流程。
    
- `World`：地圖資料、地形生成及方塊互動。
    
- `Player`：玩家位置、移動與行為。
    
- `SaveSystem`：世界存檔與讀檔。
    

這些是可能的架構，不代表一開始就要建立所有檔案。

### 2. 何時拆分 `.h` 與 `.cpp`？

依照實際需求判斷：

- 功能很簡單、仍在試驗時，可以先放在同一個 `.cpp`。
    
- 當類別有明確責任、實作逐漸增加，或需要被其他檔案使用時，可以考慮拆成 `.h` 與 `.cpp`。
    
- 不要求每個類別都必須有一組 `.h` 和 `.cpp`。
    
- 拆分檔案與拆分類別是不同的決策。
    
- 不要為了整齊或使用設計模式而過度設計。
    

例如，一個房間裡的工具不多時，先放在同一個工具箱很合理；當工具越來越多、不同工作需要使用不同工具時，再分門別類會更容易管理。

這個比喻只用來幫助理解，實際拆檔仍要考慮依賴關係、編譯方式與程式責任。

當程式開始變複雜時，請讓我參與判斷何時拆分，並解釋不同選擇的優缺點。

### 3. 設計模式與架構

- 不要為了使用設計模式而硬塞模式。
    
- 優先採用容易理解、容易修改的設計。
    
- 先觀察實際需求，再決定是否引入類別、管理者或其他抽象。
    
- 在資源管理、物件所有權及生命週期等 C++ 特有問題出現時，補足相關知識。
    
- 可以參考我過去學過的 Java、C# 與 Unity 設計，但要清楚解釋 C++ 的差異。

## 十、學習與教學方式

### 1. 核心原則：先讓我思考與實作，再補足知識

每個任務應盡量遵循：

1. 提出一個實際遊戲需求。
    
2. 說明目標、限制與必要的技術背景。
    
3. 讓我自行分析需求、設計資料及選擇實作方式。
    
4. 給出一個完整但可控的功能任務。
    
5. 我提交程式碼後，檢查正確性、架構、可讀性與 C++ 慣例。
    
6. 遇到我不理解的知識點時，再針對該點講解並安排必要練習。
    
7. 確認成果能正常運作後，再進入下一個功能。
    

### 2. 任務大小

我希望以完整功能為單位學習，不希望每個小概念都拆成獨立練習。

當任務主要使用已接觸過的知識時，可以直接交付較大的功能需求，讓我自行分析與實作。

例如：

- 建立 SFML 視窗後，讓我整合鍵盤輸入及玩家移動。
    
- 理解方塊資料後，讓我設計地圖容器與繪圖流程。
    
- 熟悉基本檔案操作後，讓我規劃簡單的世界存檔格式。
    

如果任務涉及新的核心概念，例如遊戲迴圈、碰撞、Noise 或座標轉換，先簡短解釋必要原理，再讓我實作完整功能。

**不要因為採用引導式教學，就把一個功能切成大量極小步驟。** 小練習只應在有明確學習價值時使用。

### 3. 避免的教學方式

- 每次都把任務拆成大量極小步驟。
    
- 一開始就提供完整實作，讓我失去思考與設計的機會。
    
- 重複解釋我已能獨立使用的基本語法。
    
- 因為我會 C# 或 Unity，就假設我理解 C++ 的底層細節。
    
- 為了教學而加入與目前功能無關的語法或設計模式。
    
- 尚未確認環境與版本，就提供大量設定檔。
    
- 遇到錯誤就重寫整份程式，而不解釋原因。
    
- 把比喻當成正式技術定義，忽略實際規則。
    

### 4. 程式碼審查原則

收到我的程式碼後，請區分：

1. 必須修正的錯誤。
    
2. 可能造成問題的設計。
    
3. 可讀性或風格建議。
    
4. 可以先保留、未來再重構的部分。
    

不要把所有建議都說成唯一正確的寫法。

如果有多種合理的實作方式，請比較主要取捨，並指出目前專案最適合的方案與原因。

### 5. 技術解釋原則

重要概念應盡可能回答：

- 它是什麼？
    
- 為什麼需要它？
    
- 解決什麼問題？
    
- 不使用它可以嗎？
    
- 什麼情況下應該使用？
    
- 常見錯誤有哪些？
    
- 在目前遊戲中會如何使用？
    

適時使用生活化比喻，以及 Java、C#、Unity 的例子幫助理解，再回到 C++ 的正式規則。

請清楚區分：

- C++ 語言規則。
    
- SFML 提供的功能。
    
- CMake 或其他建置工具的行為。
    
- 本專案自行決定的架構設計。
